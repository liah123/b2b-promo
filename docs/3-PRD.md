## 1. 제품 개요

### 1.1 배경
식자재를 구매하는 외식업체·급식업체 등 B2B 거래처 담당자를 대상으로, 관리자가 등록한 미션형 프로모션에 참여시키고 완료 시 "재료" 스탬프를 지급, 여러 재료를 조합한 "요리" 리워드로 교환하게 하는 참여형 프로모션 웹 서비스. 교육용 바이브코딩 실습 MVP로, 핵심 흐름(미션 참여 → 완료 → 스탬프 획득 → 리워드 교환)에 집중한다.

### 1.2 목표
- 거래처 담당자가 로그인하여 미션에 참여하고, 완료 시 스탬프를 획득해 리워드(요리)로 교환하는 전체 흐름을 웹에서 끊김 없이 수행할 수 있게 한다.
- 관리자가 미션·리워드를 직접 등록·관리하고, 미션 완료를 확인 처리할 수 있게 한다.

### 1.3 타깃 사용자
- 거래처 담당자(CUSTOMER): 외식업체·급식업체 등 B2B 거래처의 실무 담당자
- 관리자(ADMIN): 프로모션 운영 담당자

### 1.4 성공 지표 (MVP 기준)
- 핵심 플로우(회원가입/로그인 → 미션 참여 → 완료 → 스탬프 확인 → 리워드 교환) E2E 정상 동작
- 관리자 미션/리워드 CRUD 및 상태 관리 정상 동작
- 3일 내 데모 가능한 상태로 배포/실행 가능

> 참고(장기 목표, MVP 구현 범위 아님): 거래처 1,000개 이상 등록, 3,000개 이상 팀 동시 진행. 이는 스케일 가정으로만 반영하며, 3일 MVP에서는 일반적인 PostgreSQL 인덱스·커넥션 풀 수준 이상의 별도 확장 설계(샤딩, 다중 리전, 캐시 레이어 등)는 하지 않는다.

## 2. 범위

### 2.1 In-scope (도메인 정의서 MVP 포함 범위 그대로)
- 회원가입/로그인 (이메일 유일성)
- 미션 등록·조회·참여·완료
- 스탬프(재료별) 지급 및 이력 조회
- 리워드(요리) 등록·조회·교환
- 마이페이지 (내 정보 조회/수정, 비밀번호 변경)

### 2.2 Out-of-scope
- 실제 주문/결제/정산
- 실제 주문 데이터와 미션 자동 연동
- ERP·상품·재고 시스템 연동
- 실제 쿠폰 발급 시스템 연동
- 거래처 등급별 차등 혜택
- 승인 워크플로우
- 포인트·캐시
- 검색 기능
- 알림톡·SMS·푸시
- 랭킹·배지·레벨 등 추가 게이미피케이션
- 접근성 대응 (본 프로젝트에서는 고려하지 않음)

### 2.3 비즈니스 목표와 MVP 범위의 관계
- "거래처 1,000개+", "3,000개 팀 동시 진행"은 서비스가 성장했을 때의 목표치이며, 3일 MVP는 이를 위한 기능 축소·생략 없이 **핵심 도메인 로직의 정확성**에 집중한다. 동시성/부하 대응은 표준 웹 스택(Postgres 인덱스, 커넥션 풀, stateless API 서버)이 기본 제공하는 수준으로 충분하다고 가정한다.

## 3. 기능 요구사항 (액터별, 화면 단위)

### 3.1 공통 (비로그인/로그인 공통)
| 화면 | 기능 |
|---|---|
| 회원가입 | 이메일/비밀번호/이름 입력, 이메일 중복 검증, 역할은 기본 CUSTOMER로 가입 (ADMIN 계정은 회원가입 화면 없이 DB seed로 수동 생성) |
| 로그인 | 이메일/비밀번호 로그인, access token + refresh token 발급 |
| 토큰 재발급 | access token 만료 시 refresh token으로 재발급(자동, 화면 노출 없음) |
| 로그아웃 | 서버에 저장된 refresh token 폐기 + 클라이언트 토큰 삭제 |
| 인증 가드 | 미로그인 시 미션/스탬프/리워드/마이페이지 접근 불가 → 로그인 페이지로 리다이렉트 |

### 3.2 거래처 담당자 (CUSTOMER)
| 화면 | 기능 |
|---|---|
| 스탬프 홈(첫 화면) | 로그인 직후 진입, 보유 스탬프 요약 + 받을 수 있는 혜택 미리보기 + 최근 이용 내역 미리보기 |
| 스탬프 적립 안내 | 진행중/예정 적립 항목 목록 조회 (상태 표시), 각 항목의 참여 여부 표시 |
| 적립 안내 상세 | 항목 설명·진행기간·적립조건·지급 스탬프/수량 조회, 적립 요청 버튼 |
| 적립 진행 현황 | 참여중(직원 확인 대기) / 완료 항목 구분 목록 조회 |
| 적립 확인 요청/직원 확인 | 테스트용 "확인 요청" 버튼으로 적립 조건 충족 처리 → 스탬프 지급 |
| 스탬프 및 이용 내역 | 스탬프 종류별 보유 개수 조회 |
| 스탬프 이력 | 스탬프 종류별 적립/차감 이력(사유, 일시) 조회 |
| 쿠폰/혜택 목록 | 받을 수 있는 혜택 목록, 필요 스탬프(종류·수량), 받을 수 있는지 여부(보유 스탬프 기준) 표시 |
| 쿠폰 받기 | 필요 스탬프를 모두 충족한 경우 실행 → 스탬프 종류별 차감 |
| 쿠폰 사용 내역 | 본인이 받은 쿠폰/혜택 내역 조회 |
| 마이페이지 | 내 정보 조회/수정, 비밀번호 변경 |

### 3.3 관리자 (ADMIN)
| 화면 | 기능 |
|---|---|
| 적립 항목 관리 목록 | 등록된 적립 항목 목록 조회 (상태 포함) |
| 적립 항목 등록/수정 | 항목명, 설명, 참여기간(시작/종료), 적립조건, 지급 스탬프 종류(ingredientType), 지급 수량(stampCount) 입력 |
| 적립 항목 상태 관리 | 예정/진행중/종료 수동 전환 (자동 계산이 기본, 수동 종료는 예외 처리) |
| 적립 확인 처리 | 특정 사용자의 참여 건에 대해 확인 처리 (테스트용 방식과 동일 로직) |
| 혜택 관리 목록 | 등록된 쿠폰/혜택 목록 조회 |
| 혜택 등록/수정 | 혜택명, 설명, 필요 스탬프([{ingredientType, quantity}]) 입력/수정 |
| 혜택 상태 관리 | 활성/비활성 전환 |
| 마이페이지 | 내 정보 조회/수정, 비밀번호 변경 (공통과 동일) |

## 4. 비기능 요구사항

- **반응형 웹 UI**: 웹 애플리케이션 우선 개발, 모바일은 별도 앱 없이 반응형 웹(브레이크포인트 대응 레이아웃)으로 대응. 필수 적용.
- **인증**: 이메일/비밀번호 기반 인증. JWT access token(짧은 만료, API 인가용) + refresh token(긴 만료, access token 재발급용) 조합 사용. Access token 만료 시 refresh token으로 재발급받아 로그인 세션을 유지하며, 로그아웃 시 refresh token은 폐기한다. 인증 없이는 회원가입/로그인 외 API 접근 불가.
- **권한 분리**: CUSTOMER/ADMIN 역할별 접근 제어(미들웨어 수준의 role guard) — 관리자 전용 API는 ADMIN만 호출 가능.
- **성능/확장성(참고용)**: 일반적인 PostgreSQL 인덱스(예: email, userId+ingredientType, missionId+userId 조합) 및 커넥션 풀 사용 수준으로 충분. 3,000팀 동시 진행은 장기 스케일 가정이며 MVP에서 별도 부하테스트·고가용성 설계는 하지 않음.
- **접근성**: 본 프로젝트에서는 고려하지 않음 (명시적 제외).
- **오버엔지니어링 금지**: 도메인 정의서 MVP 범위를 벗어나는 기능·추상화 추가 금지.

## 5. 기술 스택 및 아키텍처 개요

### 5.1 스택
| 레이어 | 기술 |
|---|---|
| 프론트엔드 | React 19, Zustand(전역 상태), TanStack Query(서버 상태/통신) |
| 백엔드 | Node.js + Express |
| DB 접근 | pg (node-postgres) |
| 데이터베이스 | PostgreSQL 17 |

> 참고: UI 표시 문구와 내부 라우트/테이블/엔티티명은 다르다(내부명은 도메인 정의서 기준 유지, UI 문구는 `7-wireframe.md` 0장 매핑 기준).

### 5.2 레이어 구조 (개략)
```
[React 19 SPA]
  - pages: Login/Signup, StampHome(첫 화면), MissionList, MissionDetail, MyMissions,
           Stamps, RewardList, MyRedemptions, MyPage,
           Admin/MissionManage, Admin/RewardManage
  - Zustand: 로그인 사용자 정보, access token(메모리 보관)
  - TanStack Query: API 호출/캐싱/뮤테이션, access token 만료(401) 시 refresh 후 원요청 재시도

        ↓ REST API (JSON, JWT Bearer access token / refresh token은 httpOnly 쿠키)

[Express API]
  - routes: /auth(login/refresh/logout), /missions, /participations, /stamps, /rewards, /redemptions, /users(me)
  - middleware: authGuard(access token 검증), roleGuard(ADMIN 체크)
  - controllers → services(도메인 로직: 참여/완료/스탬프지급/교환 트랜잭션, 토큰 발급/재발급/폐기)
  - pg Pool을 통한 DB 접근 (트랜잭션: 완료 처리·리워드 교환 시 BEGIN/COMMIT)

        ↓

[PostgreSQL 17]
  - tables: users, missions, mission_participations, stamp_transactions,
            rewards, reward_redemptions, refresh_tokens
  - 주요 인덱스: users.email(unique), mission_participations(mission_id,user_id) unique,
                stamp_transactions(user_id, ingredient_type), reward_redemptions(user_id),
                refresh_tokens(user_id), refresh_tokens(token) unique
```
- refresh_tokens: 로그아웃/재발급 시 폐기(revoke) 처리를 위해 DB에 저장 (id, user_id, token, expires_at, revoked_at). 회전(rotation) 정책은 MVP 범위 밖 — 단순 폐기만 지원.
  - ponytail: refresh token을 DB 테이블 1개로만 관리 (Redis blacklist 등 별도 저장소 없음), 트래픽 늘면 Redis 캐시 레이어 도입 고려

- 폴더 단위 최소 3-레이어(routes/controllers-services/db)로 충분하며, 별도 도메인 계층 프레임워크·DI 컨테이너 등은 도입하지 않는다.
- 리워드 교환·미션 완료 처리는 각각 단일 DB 트랜잭션으로 원자성만 보장하면 충분(별도 큐/이벤트 시스템 불필요).

## 6. 일정 및 리소스

전제: 1인 개발, 3일 내 핵심 기능 완성.

| 일차 | 내용 |
|---|---|
| Day 1 | DB 스키마 설계·마이그레이션(refresh_tokens 포함), ADMIN 계정 seed 스크립트, 인증(회원가입/로그인/access+refresh 토큰 발급·재발급·로그아웃), 미션 CRUD(관리자) + 미션 목록/상세(거래처 담당자) |
| Day 2 | 미션 참여/완료 처리, 스탬프 지급(트랜잭션 기록), 스탬프 현황/이력 조회, 리워드 CRUD(관리자) + 리워드 목록/교환(거래처 담당자) |
| Day 3 | 마이페이지(정보수정/비밀번호변경), 반응형 UI 다듬기, 예외/에러 처리, 전체 E2E 점검 및 버그 수정(QA) |

- 리소스: 1인 풀스택 개발 전제, 별도 디자이너/QA 인력 없음 (본인이 겸임).

## 7. 리스크 및 가정

| 항목 | 내용 |
|---|---|
| 리스크: 일정 | 3일 내 1인 개발이므로 기능 추가 요청 발생 시 범위(2장) 재확인 후 우선순위 조정 필요 |
| 리스크: 미션 완료 판정 | 실제 업무 완료를 검증할 외부 연동이 없어 "테스트용 완료 처리/관리자 확인"으로 단순화 — 악용(임의 완료) 가능성은 MVP에서 허용된 가정 |
| 리스크: 동시성 | 동일 사용자의 동시 다중 요청으로 인한 중복 참여/중복 지급/중복 교환 가능성 → DB 유니크 제약(mission_participations unique) 및 트랜잭션으로 방지 |
| 가정 | 접근성, 다국어, 실결제/실주문 연동은 요구되지 않음 (도메인 정의서 제외 범위와 동일) |
| 가정 | 1,000개 거래처/3,000팀 동시 진행은 장기 목표 수치이며 MVP 단계의 실측 검증 대상이 아님 |
