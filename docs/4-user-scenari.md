# 사용자 시나리오 — Stamp Up

버전: v1.0 (작성일: 2026-08-13)
근거 문서: `docs/1-domain-definition.md` (v1.4), `docs/3-PRD.md` (v1.2)

## 액터
- 거래처 담당자 A (role=CUSTOMER)
- 관리자 B (role=ADMIN)

---

## 1. 회원가입 (거래처 담당자)

**전제**: 거래처 담당자 A가 서비스를 처음 이용하며, 아직 계정이 없다.

1. A가 회원가입 화면에서 이메일, 비밀번호, 이름을 입력한다.
2. 시스템이 이메일 중복 여부를 검증한다.
3. 중복이 없으면 role=CUSTOMER 계정이 생성된다.
4. 회원가입이 완료되고 로그인 화면으로 이동한다.

**결과**: A는 CUSTOMER 계정으로 로그인할 수 있게 된다.

---

## 2. 로그인 / 로그아웃 (거래처 담당자)

**전제**: A가 회원가입을 마쳤다.

1. A가 로그인 화면에서 이메일/비밀번호를 입력한다.
2. 시스템이 인증에 성공하면 access token과 refresh token을 발급한다.
3. A가 미션 목록 화면으로 이동하여 서비스를 이용한다.
4. A가 로그아웃 버튼을 누른다.
5. 서버에 저장된 refresh token이 폐기되고, 클라이언트의 토큰이 삭제된다.
6. 로그인 화면으로 이동하며, 이후 인증이 필요한 화면 접근 시 로그인 화면으로 리다이렉트된다.

**결과**: A는 정상적으로 로그인/로그아웃을 수행한다.

---

## 3. 미션 조회 및 참여 (거래처 담당자)

**전제**: A가 로그인한 상태이며, 관리자 B가 등록한 진행중 미션이 존재한다.

1. A가 미션 목록 화면에서 진행중/예정 미션 목록과 참여 여부를 확인한다.
2. A가 진행중인 미션 하나를 선택해 상세 화면(설명, 참여기간, 완료조건, 지급 재료/수량)을 확인한다.
3. A가 참여 버튼을 누른다.
4. 시스템이 (미션, A) 조합의 MissionParticipation을 상태 JOINED로 생성한다.
5. A가 "내 미션" 화면에서 해당 미션이 참여중 목록에 표시되는 것을 확인한다.

**결과**: A는 해당 미션에 참여중 상태가 된다.

---

## 4. 미션 완료 및 스탬프(재료) 획득 (거래처 담당자)

**전제**: A가 미션에 참여중(JOINED) 상태이다.

1. A가 "내 미션" 화면에서 참여중인 미션을 선택한다.
2. A가 테스트용 "완료 처리" 버튼을 누른다.
3. 시스템이 MissionParticipation 상태를 COMPLETED로 변경하고, 미션에 정의된 ingredientType 재료의 StampTransaction(적립, amount=stampCount)을 1건 생성한다.
4. A가 스탬프 현황 화면에서 해당 재료 종류의 보유 스탬프 개수가 증가한 것을 확인한다.
5. A가 스탬프 이력 화면에서 적립 이력(사유: 미션완료, 일시)을 확인한다.

**결과**: A는 해당 재료의 스탬프를 획득하고, 미션은 완료 목록으로 이동한다.

---

## 5. 리워드(요리) 교환 (거래처 담당자)

**전제**: A가 리워드 레시피에 필요한 모든 재료를 필요 수량 이상 보유하고 있다 (예: 카레 = 양파 2 + 당근 1, A는 양파 3·당근 2 보유).

1. A가 리워드 목록 화면에서 교환 가능한 요리 목록과 각 요리의 레시피, 교환 가능 여부를 확인한다.
2. A가 교환 가능 표시된 "카레"를 선택해 교환을 실행한다.
3. 시스템이 레시피에 명시된 재료 종류(양파 2, 당근 1)만큼 StampTransaction(차감)을 각각 생성하고, RewardRedemption을 기록한다.
4. A의 재료별 보유 스탬프가 즉시 차감된다 (양파 1개, 당근 1개 남음).
5. A가 "내 교환 내역" 화면에서 방금 교환한 카레 내역을 확인한다.

**결과**: A는 재료 스탬프를 소모하고 카레(리워드)를 교환받는다.

---

## 6. 마이페이지 (거래처 담당자)

**전제**: A가 로그인한 상태이다.

1. A가 마이페이지 화면으로 이동해 자신의 정보(이메일, 이름)를 확인한다.
2. A가 이름을 수정하고 저장한다.
3. A가 비밀번호 변경 화면에서 새 비밀번호를 입력해 변경한다.

**결과**: A의 정보와 비밀번호가 갱신된다.

---

## 7. 미션 등록 및 상태 관리 (관리자)

**전제**: 관리자 B가 로그인한 상태이다.

1. B가 미션 관리 화면에서 등록된 미션 목록(상태 포함)을 확인한다.
2. B가 "미션 등록" 화면에서 미션명, 설명, 참여기간(시작/종료), 완료조건, 지급 재료 종류(ingredientType), 지급 수량(stampCount)을 입력해 저장한다.
3. 시스템이 참여기간 기준으로 미션 상태(예정/진행중/종료)를 자동 계산한다.
4. B가 필요 시 진행중인 미션을 수동으로 "종료" 처리한다 (참여기간이 남아 있어도 강제 종료되는 예외 처리).

**결과**: 신규 미션이 등록되고, 거래처 담당자들이 조회·참여할 수 있게 된다.

---

## 8. 미션 완료 확인 처리 (관리자)

**전제**: 거래처 담당자 A가 미션에 참여중(JOINED) 상태이다.

1. B가 미션 관리 화면에서 해당 미션의 참여자 목록을 확인한다.
2. B가 A의 참여 건을 선택해 완료 확인 처리를 실행한다.
3. 시스템이 A의 완료 처리(테스트용 완료 처리와 동일 로직)를 수행하여 MissionParticipation을 COMPLETED로 변경하고 재료 스탬프를 지급한다.

**결과**: A는 관리자 확인을 통해 미션을 완료하고 스탬프를 획득한다.

---

## 9. 리워드 등록 및 상태 관리 (관리자)

**전제**: 관리자 B가 로그인한 상태이다.

1. B가 리워드 관리 화면에서 등록된 요리 목록을 확인한다.
2. B가 "리워드 등록" 화면에서 요리명, 설명, 레시피([{ingredientType, quantity}])를 입력해 저장한다.
3. 시스템이 상태를 활성(ACTIVE)으로 생성한다.
4. B가 특정 요리를 비활성(INACTIVE)으로 전환한다.

**결과**: 신규 요리가 등록되어 거래처 담당자가 교환 가능해지며, 비활성화된 요리는 신규 교환이 불가능해진다.

---

## 10. [예외] 참여 기간 종료 후 신규 참여 시도 (거래처 담당자)

**전제**: A가 조회 중인 미션의 상태가 이미 "종료(ENDED)"이다.

1. A가 미션 목록에서 종료된 미션을 선택해 상세 화면으로 이동한다.
2. 상세 화면에는 참여 버튼이 비활성화되어 있거나, A가 참여를 시도해도 시스템이 요청을 거부한다.
3. 시스템은 "참여 기간이 종료된 미션입니다" 등의 사유로 신규 참여를 생성하지 않는다.

**결과**: A는 종료된 미션에 신규 참여할 수 없으며, 기존 참여·완료 이력이 있다면 그것만 조회 가능하다.

---

## 11. [예외] 이미 완료한 미션 재완료 시도 (거래처 담당자)

**전제**: A의 MissionParticipation이 이미 COMPLETED 상태이다.

1. A가 "내 미션"의 완료 목록에서 해당 미션을 다시 연다.
2. A가 완료 처리 버튼을 다시 누른다 (또는 중복 요청이 발생한다).
3. 시스템은 해당 (미션, A) 조합이 이미 COMPLETED임을 확인하고 재완료·재지급을 거부한다.

**결과**: 스탬프는 중복 지급되지 않으며, A의 보유 스탬프는 변하지 않는다.

---

## 12. [예외] 스탬프 부족 시 리워드 교환 시도 (거래처 담당자)

**전제**: A가 "카레"(양파 2 + 당근 1) 레시피 중 당근을 0개 보유하고 있다.

1. A가 리워드 목록 화면에서 "카레"를 확인하면 교환 불가 상태로 표시된다.
2. A가 교환을 시도한다.
3. 시스템은 레시피의 모든 재료 중 하나라도 필요 수량 미만이면 교환을 거부한다 (부분 재료 보유로는 교환 불가).

**결과**: RewardRedemption과 StampTransaction(차감)이 생성되지 않으며, A의 재료 스탬프는 그대로 유지된다.

---

## 13. [예외] 비활성 리워드 교환 시도 (거래처 담당자)

**전제**: 관리자 B가 "카레" 리워드를 비활성(INACTIVE) 상태로 전환했다.

1. A가 리워드 목록 화면에서 "카레"를 조회한다 (비활성 표시 또는 목록 미노출).
2. A가 필요 재료를 모두 보유하고 있음에도 교환을 시도한다.
3. 시스템은 리워드 상태가 비활성임을 확인하고 신규 교환을 거부한다.

**결과**: 비활성 리워드는 교환되지 않는다.

---

## 14. [예외] 이메일 중복 가입 시도 (거래처 담당자)

**전제**: 이미 특정 이메일로 가입된 계정이 존재한다.

1. 신규 사용자가 회원가입 화면에서 이미 사용 중인 이메일을 입력한다.
2. 시스템이 이메일 중복 여부를 검증한다.
3. 중복이 확인되어 "이미 가입된 이메일입니다" 등의 오류를 반환하고 계정을 생성하지 않는다.

**결과**: 동일 이메일로 중복 가입되지 않으며, 사용자는 다른 이메일로 재시도하거나 기존 계정으로 로그인해야 한다.
